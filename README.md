# Elsewhere

Elsewhere помогает спланировать поездку, когда вы уже понимаете, **как хотите отдохнуть**, но ещё не решили,
куда ехать.

Вместо десятков фильтров можно написать обычную фразу:

> Хотим вдвоём на неделю к тёплому морю. Бюджет — до 180 000 ₽. Без толп, вкусно есть и много гулять.

Система разберёт пожелания, предложит несколько действительно разных сценариев и покажет, чем придётся
пожертвовать в каждом из них. Любой вариант можно сделать дешевле, спокойнее или удобнее и сразу увидеть,
как изменятся цена, совпадение с мечтой и риски.

```text
Мечта → варианты поездки → симуляция → прогноз рисков → план
```

Elsewhere ничего не бронирует и не принимает оплату. На выходе получается объяснимый план поездки, который
можно использовать для принятия решения.

## Быстрый запуск

Понадобятся Git, Node.js и либо Ruby 3.3+, либо Docker.

```bash
bin/setup
```

Команда установит зависимости, подготовит базу и подключит git-хуки. Если подходящего Ruby на машине нет,
она сама использует Docker.

Запустите backend:

```bash
bin/rails server
```

Если setup выбрал Docker:

```bash
docker compose up app
```

В другом терминале запустите интерфейс:

```bash
npm install --prefix web
npm run dev --prefix web
```

- интерфейс: <http://localhost:5173>
- API: <http://localhost:3000>

По умолчанию проект работает в режиме `fixture`: для первого запуска не нужны API-ключи или локальная LLM.

## Что можно сделать

### 1. Описать поездку своими словами

Из текста собирается **Travel DNA** — набор предпочтений, ограничений и их приоритетов. Его можно проверить и
исправить руками: последнее слово всегда остаётся за пользователем.

### 2. Сравнить разные варианты будущего

**Futures** — не три соседние позиции из одного рейтинга. Система старается показать лучший вариант, более
дешёвую альтернативу и сценарий с другой географией. Если по-настоящему разных вариантов меньше трёх, она так
и скажет.

### 3. Подвинуть условия

В **Simulator** можно попросить «сделай дешевле», «хочу больше тишины» или изменить параметр ползунком.
Исходный вариант не перезаписывается: создаётся новая версия и понятная дельта стоимости и совпадения.

### 4. Посмотреть риски до поездки

**Forecast** показывает только релевантные этому путешественнику риски: например, холодное море, сложный
трансфер или вероятный шум. У каждого вывода есть измерение, источник и свежесть. Если данных не хватило, это
указано прямо.

### 5. Получить цельный план

**Trip Plan** объединяет перелёт, проживание и трансферы. Общая сумма всегда складывается из видимых компонентов,
а рядом с каждой цифрой указано, наблюдалась она или была смоделирована.

## Откуда берутся данные

| Данные | Источник | Как используются |
|---|---|---|
| Объекты размещения | локально сохранённый каталог | реальные характеристики и базовый ценовой уровень |
| Берег, дороги, POI и аэропорты | OpenStreetMap + PostGIS | расстояния и характеристики окружения |
| Климат и погода | Open-Meteo | климатические нормы и актуальный прогноз |
| Авиатарифы | Ignav | живые цены в режиме `live` |
| Цена номера на выбранные даты | собственная модель | наблюдаемая база с явно смоделированной сезонностью |
| Отзывы | источник не подключён | выводы по отзывам не строятся |

В демонстрационном корпусе 408 объектов в семи направлениях: Анапа, Сочи, Калининград, Казань,
Санкт-Петербург, Кавказские Минеральные Воды и Шерегеш.

## Как проект обращается с неопределённостью

- LLM помогает понять и сформулировать текст, но не рассчитывает цены, баллы или расстояния.
- Балл совпадения можно разложить по отдельным предпочтениям.
- Риск не появляется без измерения или явно обозначенного косвенного показателя.
- Непроверенное значение не считается нейтральным — оно остаётся непроверенным с объяснением причины.
- Симуляция создаёт новую версию Future и не меняет прошлое задним числом.
- Сезонная цена номера помечается как `modeled`; наблюдаемые данные не выдаются за модель и наоборот.

## Технологии и устройство репозитория

Backend — Ruby 3.3 и Rails 8.1. Это модульный монолит с границами Packwerk, PostgreSQL/PostGIS, Redis и Sidekiq.
Frontend написан на React и TypeScript; API-клиент следует OpenAPI-контракту, а тестовые ответы подменяются MSW.
Для языковой модели используется OpenAI-совместимый endpoint, например Ollama или LM Studio.

```text
packs/
  shared/       общие value objects и запуск AI-задач
  supply/       каталог, тарифы, климат, география и модель цены
  planning/     Travel DNA, ограничения, подбор, сборка и симулятор
  foresight/    доказательства, правила рисков и способы их смягчить
app/            HTTP-контроллеры и фоновые задачи
web/            React-интерфейс
spec/           backend-тесты и сквозные сценарии
docs/           продуктовые решения, архитектура, исследования и контракты
```

Основная логика живёт в пакетах, а не в контроллерах. Зависимости направлены в одну сторону:
`shared ← supply ← planning ← foresight`. Доступ к внешним источникам сосредоточен в `supply`.

## Конфигурация

`bin/setup` создаёт `.env` из `.env.example`. Самые важные настройки:

- `SUPPLY_MODE=fixture` — автономный демонстрационный режим;
- `SUPPLY_MODE=live` — реальные поставщики, нужны `IGNAV_API_KEY` и `ORS_API_KEY`;
- `LLM_BASE_URL` и `LLM_MODEL` — адрес и имя локальной или удалённой модели;
- `LLM_TIMEOUT_SECONDS` — максимальное время ответа модели.

Если LLM недоступна, система использует детерминированный запасной путь и помечает результат как
деградировавший, а не падает молча.

## Проверки

Полная проверка backend, границ пакетов и frontend:

```bash
bin/check
```

Тесты интерфейса:

```bash
npm test --prefix web
```

Один сквозной backend-сценарий:

```bash
RAILS_ENV=test bundle exec rspec spec/requests/phase_zero_spec.rb
```

Перед push тот же `bin/check` запускается git-хуком.

## Текущие границы

- Это планировщик, а не сервис бронирования.
- Живой режим зависит от доступности и ключей внешних поставщиков.
- Отзывы пока не подключены, поэтому риски по отзывам не симулируются.
- Цена проживания на конкретные даты включает модельную сезонность и всегда маркируется соответствующим образом.
