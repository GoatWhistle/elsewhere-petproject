# Обзор архитектуры

---

## Форма

Две развёртываемые единицы и одна база данных.

| Компонент | Технология | Почему |
|---|---|---|
| `elsewhere-api` | Ruby on Rails, модульный монолит, пакеты принуждаются packwerk | DEC-002; границы без цены сервисов |
| `elsewhere-web` | React и TypeScript, клиент генерируется из `openapi.yaml` | Другая среда выполнения и сборка; собирается против моков до появления бэкенда |
| PostgreSQL | плюс PostGIS (географические признаки), плюс pgvector *только если* семантический поиск окажется необходим | Одно хранилище, одна история резервных копий, одна транзакционная граница |
| Redis и Sidekiq | фоновые задачи | Каждая медленная операция — задача (принцип API 3) |

Ни брокера сообщений, ни микросервисов. После удаления Living Trip ([DEC-015](../00_project/decision_log.md))
потока событий нет вообще — только фоновые задачи. [DEC-002](../00_project/decision_log.md) требует причины для
каждой зависимости, а не эстетики.

## Почему модульный монолит здесь уместен

Обычный аргумент — скорость. Более сильный аргумент в этом проекте другой: **все контексты разделяют одну
транзакционную правду**. Версия Future, её компоненты цены, вклады в совпадение и её прогноз обязаны быть
взаимно согласованы в момент, когда пользователь принимает решение. Разделение на сервисы купило бы независимое
развёртывание и заплатило бы работой над распределённой согласованностью, у которой нет продуктового
обоснования.

Границы при этом важны — отсюда packwerk. Нужна принуждаемая модульность без сетевых вызовов между своими же
модулями.

## Пути запросов

**Быстрый путь (синхронный):** чтения. `GET /futures/{id}`, `GET /forecast`.
Всё уже посчитано и сохранено.

**Медленный путь (задачи):** `POST …/futures`, `POST …/simulations`, применение смягчения.
Все возвращают `202` и `Job`; клиент опрашивает `GET /jobs/{id}`.

Разделение — не преждевременная оптимизация. Генерация Futures трогает API поставщиков, географические вычисления,
оценку и объяснение от модели: сотни миллисекунд в лучшем случае, секунды, когда поставщик тормозит. В условиях
демонстрации синхронная генерация — ровно тот способ, которым получают таймаут на глазах у зала.

## Поток данных: от Мечты к Futures

```
POST /planning-sessions
  → Planning: модель извлекает кандидатов в элементы Travel DNA (структурированный вывод, проверенный схемой)
  → Planning: сильно влияющие неоднозначности становятся Clarifications, а не допущениями
POST /planning-sessions/{id}/futures            → Job
  → Planning: candidate destinations       ← Supply::Catalog + Supply::Flights.directions_from
  → Planning: hard-constraint filter        (deterministic; a violation disqualifies, it does not score low)
  → Planning: room rates per candidate      ← Supply::Rates.for  (modeled)
  → Planning: features per candidate        ← Supply::Geo, Supply::Climate
  → Planning: Experience Match              (deterministic, weighted, decomposed)
  → Planning: diversity selection           (explicit objective, not a side effect of ranking)
  → Planning: trip assembly                 (travel legs + stay + transfer + mobility)
  → Planning: cost assembly                 (observed fares + modeled rate/transfer/mobility)
  → Planning: LLM writes explanations       (over numbers already computed — it never produces the numbers)
  → persist immutable Future versions
```

## Поток данных: симуляция

```
POST /futures/{id}/simulations                  → Job
  → если пришла `instruction`: модель отображает естественный язык в Adjustments (проверка схемой, закрытый словарь)
  → Planning: применение корректировок к рабочей копии Travel DNA
  → Planning: пересчёт решения
        · локально по уже полученным кандидатам, если изменились только веса
        · с новым запросом к Supply, если изменились даты, направление или состав
  → Planning: вычисление Delta (точная арифметика, по пунктам, с названным ослабленным измерением)
  → Foresight: перепроверка рисков на новой версии → new_risks / resolved_risks
  → сохранение НОВОЙ версии с parent_id
```

Разделение «локально или заново» — главное решение о производительности в системе. Большая часть дёшева: каталог,
географические признаки и модель цены номера локальны. Через сеть ходят только авиатарифы.

## Где риск на самом деле

Не в масштабировании и не в выборе фреймворка. Настоящих рисков три:

1. **Разнообразие.** Если три Future возвращаются похожими друг на друга, посылка продукта проваливается в первые
   двадцать секунд. Смягчается тем, что разнообразие сделано явной целью отбора с измеримым разбросом по
   измерениям DNA.
2. **Качество доказательств.** Одно уверенно ошибочное утверждение о риске уничтожает доверие ко всем остальным.
   Смягчается через `claim_kind`, обязательные доказательства и отчёт о покрытии (DEC-011).
3. **Честность цены.** Цена номера модельная, а тариф настоящий, и оба под одной суммой, о которой рассуждает
   пользователь. Смягчается структурно через `PriceComponent.fulfilment` в контракте API и тем, что об этом
   говорится вслух.

Всё остальное — обычная инженерия.
