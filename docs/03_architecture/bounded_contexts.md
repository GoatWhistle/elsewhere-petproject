# Ограниченные контексты

Три контекста внутри одного модульного монолита на Rails (DEC-002) плюс приложение фронтенда.
Каждый контекст владеет своими таблицами, своим словарём и своим публичным интерфейсом. Через границу ничто не
дотягивается иначе как через этот интерфейс.

---

## Карта

```
                    ┌──────────────────────────────────────────┐
                    │            ФРОНТЕНД (React + TS)         │
                    │      говорит только с публичным API      │
                    └───────────────────┬──────────────────────┘
                                        │  openapi.yaml
        ┌───────────────────────────────┴──────────────────────────────┐
        │                 Модульный монолит на Rails                   │
        │                                                              │
        │   ┌───────────┐      ┌────────────┐                          │
        │   │ PLANNING  │─────▶│ FORESIGHT  │                          │
        │   │ dna       │      │ риски      │                          │
        │   │ futures   │◀─────│ смягчения  │                          │
        │   │ match     │      └─────┬──────┘                          │
        │   │ simulator │            │                                 │
        │   └─────┬─────┘            │                                 │
        │         │                  │                                 │
        │         └──────────┬───────┘                                 │
        │                    ▼                                         │
        │              ┌───────────┐                                   │
        │              │  SUPPLY   │  единственный код, который        │
        │              │поставщики │  говорит с внешним миром          │
        │              │ география │                                   │
        │              │ климат    │                                   │
        │              └───────────┘                                   │
        └──────────────────────────────────────────────────────────────┘
                    │              │                │
       собранный каталог    тарифы Ignav    Open-Meteo / выгрузка OSM
```

Стрелки — направление зависимости. **Supply не зависит ни от чего внутреннего.** Planning зависит только от
Supply. Foresight зависит от Supply и читает Future из Planning.

---

## SUPPLY — внешний мир, и только здесь

**Ответственность.** Всё внешнее, приведённое к внутренним значимым объектам. Если сетевой вызов к третьей
стороне существует где-то ещё в коде — это баг.

**Владеет:** конвейером сбора каталога, моделью цены номера, адаптером Ignav, хранилищем географических признаков
в PostGIS, построенным из выгрузки OSM, климатическими нормами из Open-Meteo и захваченными фикстурами.

**Публичный интерфейс (Ruby):** `Supply::Catalog`, `Supply::Offers`, `Supply::Flights`, `Supply::Geo`,
`Supply::Climate`, `Supply::Rates`, `Supply::Reviews`. См. [provider_adapters.md](../04_api/provider_adapters.md).

**Свои таблицы:** `destinations`, `properties`, `property_geo_features`, `destination_climate_normals`,
`price_calibrations`, `flight_fare_snapshots`.

**Зачем эта граница.** Здесь встречаются данные четырёх разных сортов: локально собранный каталог, локальные
географические признаки, живые внешние тарифы и одна **модельная** величина. Что из этого чем является, не должно
протекать наверх особым случаем в каждом вызывающем — Supply единственное место, которое знает, что число
наблюдали, а не сгенерировали, и говорит об этом при каждом чтении.

**Поведение при отказе.** Никогда не выбрасывает ошибки поставщика наверх. Возвращает результаты с метаданными
`freshness` и `availability` либо явное значение `Unavailable`. Дальше по цепочке снижается уверенность, а не
падает система.

## PLANNING — движок решений

**Ответственность.** Мечта → Travel DNA → Futures → симуляция. Всё, что решает, *что предложить и почему*.

**Владеет:** построением и правкой Travel DNA, фильтрацией по жёстким ограничениям, оценкой Совпадения,
оркестрацией отбора кандидатов, выбором разнообразия, переоптимизацией при симуляции, вычислением дельты.

**Публичный интерфейс:** `Planning::Sessions`, `Planning::TravelDna`, `Planning::Futures`, `Planning::Simulator`.

**Свои таблицы:** `planning_sessions`, `travel_dna_elements`, `clarifications`, `futures`, `future_versions`,
`future_components`, `match_scores`, `match_contributions`, `deltas`, `delta_items`.

**Зачем эта граница.** Это продуктовый тезис в коде. Он обязан быть детерминированным, тестируемым в изоляции и
сравнимым между версиями. Он говорит с Supply через один интерфейс и ничего не знает о бронировании, прогнозе и
HTTP.

**Инвариант, который он держит:** версия Future неизменяема. Симуляция пишет новую версию, а не обновляет старую.

---

## FORESIGHT — доказательства в риски

**Ответственность.** Превращать доказательства в пункты риска, релевантные *этой* Travel DNA, и предлагать
смягчения.

**Владеет:** получением и извлечением доказательств, правилами рисков, вычислением серьёзности и уверенности,
отчётом о покрытии, предложениями смягчений.

**Публичный интерфейс:** `Foresight::Forecasts`.

**Свои таблицы:** `forecasts`, `risk_items`, `risk_evidence`, `mitigations`.

**Зачем эта граница.** Его источники данных — самые неопределённые в проекте (DEC-011), поэтому он обязан уметь
деградировать, сообщая `coverage: assessed=false, reason: ...`, так, чтобы ни один другой контекст этого не
заметил.

**Правило, которое не даёт ему протечь в Planning:** смягчение *описывается*, а не применяется. Foresight выдаёт
смягчение с полезной нагрузкой корректировки; применяет её вызов `Planning::Simulator`. **Foresight никогда не
пишет Future.** Это самое важное правило границы в системе, потому что именно его будет соблазн нарушить.

## ФРОНТЕНД — React и TypeScript

**Ответственность.** Весь пользовательский опыт, против замороженного публичного API.

**Владеет:** приложением на React, сгенерированным клиентом на TypeScript и обработчиками моков MSW,
сгенерированными из того же документа OpenAPI.

**Почему отдельная развёртываемая единица.** Другая среда выполнения, другой язык, другой конвейер сборки и —
практическая причина — его можно довести до конца против моков раньше, чем заработает хоть один эндпоинт.

## Правила, которые держат границы

1. **Никакого доступа к чужой базе.** Контекст читает свои таблицы. Всё прочее приходит через интерфейс.
2. **Никаких чужих моделей ActiveRecord.** Интерфейсы возвращают простые значимые объекты, а не записи.
3. **Границы принуждаются механически**, а не дисциплиной — пакеты `packwerk` с объявленными зависимостями.
4. **Только одно направление.** Supply → ни на что. Planning → Supply. Foresight → Supply и чтение Future.
   От Foresight не зависит ничто.
5. **Общая схема, а не общий код.** Схема Future определена однажды (в Planning) и потребляется как значимый
   объект. Контексты не лезут в чужую логику, чтобы пересчитать её заново.

## Жизненный цикл версии Future

```
создана ──▶ (неизменяема)
   │
   ├── симуляция ──▶ новая версия (задан parent_id, вычислена дельта)
   ├── смягчение ──▶ новая версия (тот же путь — смягчение ЭТО симуляция)
   └── истечение ──▶ устарела (наблюдаемый тариф состарился; перезапросить, прежде чем показывать как текущий)
```

Перехода «обновлена» нет по замыслу. Неизменяемость и делает отмену, сравнение и вычисление дельты тривиальными
вместо задачи восстановления. Это же единственный оставшийся в системе автомат состояний: без заказов и без денег
([DEC-018](../00_project/decision_log.md)) жизненного цикла больше нет ни у чего.
