# Архитектура ИИ

---

## Управляющее правило

> **Модель может читать язык и писать язык. Владеть числами она не может.**

У каждого вызова модели в Elsewhere есть определённый вход, определённая схема выхода, детерминированный запасной
путь и задокументированное поведение при отказе. Свободно бродящего исполнителя в пути запроса нет.

## Четыре задачи для модели

| # | Задача | Вход | Выход | Если не удалась |
|---|---|---|---|---|
| 1 | **Разбор Мечты** | свободный текст и структурированные поля | кандидаты `TravelDnaElement[]`, `Clarification[]`, `unmatched_intent[]` | Спросить пользователя формой напрямую. Продукт деградирует до явного ввода, а не до бессмыслицы. |
| 2 | **Интерпретация инструкции** | «сделай дешевле, не повредив ничего важного» и текущая DNA | `Adjustment[]` из **закрытого словаря** измерений и направлений | Откатиться к ползункам; сказать пользователю, что мы не поняли. |
| 3 | **Порождение объяснений** | уже посчитанные вклады, дельты, цены | проза: `why_this_exists`, плюсы, компромиссы, объяснение дельты | Отрисовать шаблонное объяснение из тех же чисел. Показу Future это никогда не мешает. |
| 4 | **Извлечение доказательств из отзывов** | найденные документы отзывов, когда они есть | утверждения о риске, каждое со ссылкой на конкретный отзыв и дату | Пропустить риски из отзывов; `coverage.assessed = false` с причиной. |

## Что намеренно НЕ отдано модели

| Задача | Почему детерминированно |
|---|---|
| Фильтрация по жёстким ограничениям | Обязана быть точной и проверяемой. Потолок бюджета — не пожелание. |
| Оценка Совпадения | Обязана быть устойчивой, раскладываемой, сравнимой. «92% → 90%» бессмысленно, если число едет при перезагрузке. |
| Арифметика цен и дельт | Деньги. Никогда не приближаются. |
| Выбор разнообразия | Разнообразие обязано быть доказуемым, измеряемым как разброс по измерениям DNA. |
| Модель цены номера | Обязана быть детерминированной для объекта и дат, иначе дельты Симулятора превращаются в шум. |
| Вычисление географических признаков | PostGIS делает это точно, локально и бесплатно. |

Это разделение — не консерватизм. Оно и делает продукт объяснимым: оценку, порождённую моделью, нельзя разложить,
а вся ценность симулятора — в разложении.

## Структурированный вывод, принуждаемый

Каждый вызов идёт через один исполнитель:

```ruby
AI::Task.run(
  task: :dream_parsing,
  input: {...},
  schema: AI::Schemas::TRAVEL_DNA_CANDIDATES,   # JSON Schema, проверяется при возврате
  fallback: ->(_) { AI::Fallbacks.dream_parsing_form }
)
```

Rules the runner enforces:

- output is validated against a JSON Schema; a malformed response is retried once, then falls back;
- `AI::Client` returns `AI::Client::Result(value:, usage:)`; an array is always a domain value and is never
  overloaded as a transport tuple;
- outputs are constrained to closed vocabularies where one exists (dimensions, directions, risk types) —
  the model may not invent a dimension;
- a transport failure opens a short circuit immediately, without spending a second timeout; calls use the
  deterministic fallback until the circuit closes;
- a broken fallback cannot turn model unavailability into a 500: the runner logs `fallback_error` and returns a
  neutral value derived from the declared schema;
- every call is logged with prompt, response, latency, and cost, because evaluating quality later requires it;
- no tool has a side effect. The model never books, never cancels, never writes a Future.

## No agent loops

With Living Trip out of scope ([DEC-015](../00_project/decision_log.md)), nothing in the product needs multi-step
tool use. Every AI job above is a single structured call with a validated schema and a deterministic fallback.

An agent loop would add latency, nondeterminism, and cost to problems a single call already solves. The product is
AI-native because AI does the language work where language is the problem — not because a loop is running.

## Поиск кандидатов

Для MVP отбор кандидатов детерминирован: фильтрация корпуса по жёстким ограничениям, затем географические и
климатические признаки, затем оценка. **Никакого векторного хранилища, пока не продемонстрирована задача поиска**,
которую ранжирование по корпусу из нескольких десятков направлений не решает.

`pgvector` станет оправданным, когда доказательства из отзывов появятся в объёме и семантическое сопоставление
фрагментов отзывов с понятиями предпочтений (задача 4) начнёт требовать масштаба. Это реальная возможность, а не план.

## Оценка качества

Эталона для «был ли это хороший вариант поездки» не существует. Дешёвый и действенный заменитель:

1. **Регрессионный набор персон.** Около десяти написанных вручную Мечт с ожидаемыми исходами: какие жёсткие
   ограничения обязаны выполниться, какие измерения обязаны доминировать, какие направления обязаны или не должны
   появиться. Гоняется при каждом изменении оценки.
2. **Метрика разнообразия.** Измеренный разброс возвращённого набора по взвешенным измерениям DNA, проверяется в
   тестах. Именно она автоматически ловит худший провал продукта.
3. **Проверка атрибуции доказательств.** Каждое утверждение о риске обязано ссылаться на найденный документ;
   утверждения без ссылки отбрасываются до показа пользователю, и отбрасывание логируется.
4. **Проверка детерминированности.** Та же сессия, те же входы, та же оценка. Ловит случайное протекание модели
   в числа.
